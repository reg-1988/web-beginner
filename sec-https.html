HTTPS 与安全

HTTPS 是 Web 安全的传输基础——理解 TLS 握手、证书体系、混合内容策略，才能构建安全的 Web 应用。

1. 核心概念与定义

HTTPS是在 HTTP 基础上加入 TLS（Transport Layer Security）加密层，提供加密传输、身份验证和数据完整性三大安全保障。

HTTP 的问题：明文传输（可被窃听）、无身份验证（可被冒充）、无完整性校验（可被篡改）。HTTPS 通过 TLS 解决了这三个问题。

2. 关键特性与工作原理

2.1 TLS 握手流程

text">客户端                              服务器
  |                                    |
  |--- ClientHello ------------------→|  支持的 TLS 版本、加密套件、随机数
  |                                    |
  |←-- ServerHello -------------------|  选定的加密套件、随机数
  |←-- Certificate -------------------|  服务器证书链
  |←-- ServerKeyExchange ------------|  (可选) DH 参数
  |←-- ServerHelloDone --------------|
  |                                    |
  |--- ClientKeyExchange ------------→|  预主密钥/DH 公钥
  |--- ChangeCipherSpec ------------→|  切换到加密通信
  |--- Finished ---------------------→|  验证握手完整性
  |                                    |
  |←-- ChangeCipherSpec --------------|  切换到加密通信
  |←-- Finished -----------------------|  验证握手完整性
  |                                    |
  |←====== 加密数据传输 =========→|  使用协商的对称密钥

TLS 1.3 优化：1-RTT 握手（合并步骤），0-RTT 恢复

2.2 HTTPS 的三大保障

保障机制防什么
加密对称加密（AES-GCM）传输数据窃听（中间人截获）
认证CA 签发的数字证书验证身份冒充（钓鱼网站）
完整性MAC（消息认证码）校验数据篡改（中间人修改）

2.3 证书体系

text">根 CA（DigiCert, Let's Encrypt, ...）
  └── 中间 CA
      └── 终端证书（example.com）

证书链验证：
1. 浏览器收到服务器证书 + 中间 CA 证书
2. 用中间 CA 公钥验证服务器证书签名
3. 用根 CA 公钥验证中间 CA 证书签名
4. 根 CA 证书预装在浏览器/操作系统中

证书包含：域名、有效期、公钥、CA 签名

2.4 混合内容

类型示例浏览器行为
被动混合内容<img>, <audio>, <video>可能加载但警告
主动混合内容<script>, <link>, <iframe>, XHR默认阻止

示例一：HSTS 配置

HTTP# HSTS：强制浏览器始终使用 HTTPS
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

# 参数说明：
# max-age=31536000    — 1 年内强制 HTTPS
# includeSubDomains   — 所有子域名也强制
# preload             — 加入浏览器 HSTS 预加载列表

# Nginx 配置
server {
    listen 80;
    server_name example.com;
    return 301 https://$server_name$request_uri;
}

server {
    listen 443 ssl http2;
    server_name example.com;
    
    ssl_certificate /etc/ssl/certs/example.com.crt;
    ssl_certificate_key /etc/ssl/private/example.com.key;
    
    # 安全头部
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-XSS-Protection "1; mode=block" always;
    add_header Content-Security-Policy "default-src 'self'" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
}

JavaScript// 检测页面中的混合内容
function findMixedContent() {
  const issues = [];

  // 检查图片
  document.querySelectorAll('img[src^="http:"]').forEach(el => {
    issues.push({ type: 'img', src: el.src });
  });

  // 检查脚本
  document.querySelectorAll('script[src^="http:"]').forEach(el => {
    issues.push({ type: 'script', src: el.src });
  });

  // 检查样式表
  document.querySelectorAll('link[href^="http:"]').forEach(el => {
    issues.push({ type: 'stylesheet', href: el.href });
  });

  // 检查 iframe
  document.querySelectorAll('iframe[src^="http:"]').forEach(el => {
    issues.push({ type: 'iframe', src: el.src });
  });

  return issues;
}

示例三：安全头部最佳实践

HTTP# 完整的安全响应头配置

# 1. HSTS：强制 HTTPS
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

# 2. X-Content-Type-Options：防止 MIME 类型嗅探
X-Content-Type-Options: nosniff

# 3. X-Frame-Options：防止点击劫持
X-Frame-Options: SAMEORIGIN
# DENY — 完全不允许嵌入
# SAMEORIGIN — 同源允许

# 4. CSP：内容安全策略（防 XSS）
Content-Security-Policy: default-src 'self'; script-src 'self'

# 5. Referrer-Policy：控制 Referer 发送
Referrer-Policy: strict-origin-when-cross-origin
# 跨站请求只发送 origin，不发送完整 URL

# 6. Permissions-Policy：限制浏览器 API
Permissions-Policy: camera=(), microphone=(), geolocation=(self)

# 7. X-XSS-Protection（旧浏览器，已被 CSP 替代）
X-XSS-Protection: 1; mode=block

示例四：Certificate Pinning（证书钉扎）

JavaScript// 前端无法直接实现 Certificate Pinning（浏览器不支持）
// 但可以通过 Public Key Pinning 思想增强安全性

// 方案一：HPKP（已废弃，不推荐）
// 方案二：使用自定义 HTTPS 代理验证证书

// 方案三（移动端）：App 端实现证书钉扎
// Android: OkHttp CertificatePinner
// iOS: URLSession delegate 验证证书

// 前端替代方案：验证关键 API 响应的签名
async function fetchWithVerification(url) {
  const response = await fetch(url);
  const signature = response.headers.get('X-Response-Signature');
  const data = await response.text();
  
  // 使用预置公钥验证签名
  const verified = await verifySignature(data, signature, PUBLIC_KEY);
  if (!verified) {
    throw new Error('响应签名验证失败，可能被篡改');
  }
  return JSON.parse(data);
}

4. 常见问题与坑点

HTTPS 会影响性能吗？ +

TLS 握手增加 1~2 个 RTT（TLS 1.3 仅 1 RTT），会话恢复可 0-RTT。加密解密的 CPU 开销在现代硬件上可忽略（AES-NI 硬件加速）。HTTP/2 必须用 HTTPS，且性能优于 HTTP/1.1。总体而言：HTTPS 性能损耗很小，安全收益巨大。

自签名证书能用于生产环境吗？ +

不能。自签名证书不受浏览器信任，会显示安全警告。用户可能被训练成忽略警告，导致真正的钓鱼攻击无法识别。生产环境使用 CA 签发的证书（Let's Encrypt 免费获取）。自签名仅用于本地开发。

🚫 HSTS preload 不可轻易撤销

加入 HSTS preload 列表后，需要提交删除请求才能移除，过程可能需要数周。在确定网站长期支持 HTTPS 之前，不要添加 preload。先用较短的 max-age（如 300）测试。

⚠ HTTPS 页面中不能有 HTTP 资源

混合内容会被浏览器阻止（主动内容）或标记警告（被动内容）。迁移到 HTTPS 时，确保所有资源（图片、脚本、字体、API）都使用 HTTPS。CSP 的 upgrade-insecure-requests 可以自动升级，但第三方资源需确认支持 HTTPS。

1HTTPS 的工作原理？TLS 握手过程？
HTTPS = HTTP + TLS。TLS 握手：① 客户端发送支持的加密套件和随机数；② 服务器选择套件、返回证书和随机数；③ 客户端验证证书、生成预主密钥并用服务器公钥加密发送；④ 双方根据随机数和预主密钥计算对称密钥；⑤ 后续用对称密钥加密通信。TLS 1.3 优化为 1-RTT。
2什么是 HSTS？为什么需要它？
HSTS（HTTP Strict Transport Security）告诉浏览器在指定时间内始终使用 HTTPS 访问网站。需要它的原因：首次访问 HTTP 时可能被中间人劫持（SSL Stripping），HSTS 让浏览器记住必须用 HTTPS，跳过 HTTP 直接访问 HTTPS。preload 机制解决首次访问问题。
