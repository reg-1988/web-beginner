跨域与安全策略

同源策略是浏览器安全的基石，跨域限制让前后端分离项目面临挑战——理解同源策略、CORS 机制和各种跨域方案，是前端开发者的必备技能。

1. 核心概念与定义

同源策略（Same-Origin Policy, SOP）是浏览器最基本的安全机制，限制一个源的文档或脚本与另一个源的资源进行交互。两个 URL 具有相同的协议（protocol）、域名（host）和端口（port）时才同源。

同源策略主要限制三个方面：DOM 访问（不能读取不同源的 iframe/窗口的 DOM）、数据访问（不能读取不同源的 Ajax 响应）、Cookie/Storage 访问（不能读取不同源的存储数据）。

CORS（Cross-Origin Resource Sharing）是 W3C 标准的跨域解决方案，通过 HTTP 头部告诉浏览器允许哪些跨域请求。它是目前最主流、最规范的跨域方案。

2. 关键特性与工作原理

2.1 同源判断

URL AURL B是否同源原因
https://a.com/pagehttps://a.com/other✅ 同源协议/域名/端口相同
https://a.comhttp://a.com❌ 跨域协议不同
https://a.comhttps://www.a.com❌ 跨域域名不同
https://a.comhttps://a.com:8080❌ 跨域端口不同
https://a.comhttps://127.0.0.1❌ 跨域域名和IP不等价

2.2 CORS 请求分类

类型条件特点
简单请求GET/HEAD/POST + 标准 Content-Type + 无自定义头直接发送，浏览器自动加 Origin
预检请求（Preflight）PUT/DELETE/PATCH / 自定义头 / 非 standard Content-Type先发 OPTIONS 请求，通过后再发实际请求

2.3 CORS 关键头部

头部方向说明
Origin请求 →浏览器自动添加，表示请求来源
Access-Control-Allow-Origin← 响应允许的源（* 或具体源）
Access-Control-Allow-Methods← 响应允许的 HTTP 方法
Access-Control-Allow-Headers← 响应允许的请求头
Access-Control-Allow-Credentials← 响应是否允许携带 Cookie
Access-Control-Max-Age← 响应预检请求缓存时间（秒）
Access-Control-Expose-Headers← 响应允许前端读取的响应头

方案原理优点缺点

3. 代码示例与最佳实践

示例一：Node.js CORS 中间件

JavaScript// Express CORS 中间件（完整版）
function cors(options = {}) {
  const {
    origin = '*',           // 允许的源
    methods = ['GET', 'POST', 'PUT', 'DELETE', 'PATCH'],
    allowedHeaders = ['Content-Type', 'Authorization'],
    exposedHeaders = [],
    credentials = false,
    maxAge = 86400,         // 预检缓存 24 小时
  } = options;

  return (req, res, next) => {
    // 处理 Origin
    const requestOrigin = req.headers.origin;
    if (typeof origin === 'function') {
      // 动态判断是否允许
      const allowed = origin(requestOrigin);
      if (allowed) res.setHeader('Access-Control-Allow-Origin', requestOrigin);
    } else if (origin === '*') {
      res.setHeader('Access-Control-Allow-Origin', '*');
    } else if (Array.isArray(origin) && origin.includes(requestOrigin)) {
      res.setHeader('Access-Control-Allow-Origin', requestOrigin);
    }

    res.setHeader('Access-Control-Allow-Methods', methods.join(', '));
    res.setHeader('Access-Control-Allow-Headers', allowedHeaders.join(', '));
    
    if (credentials) {
      res.setHeader('Access-Control-Allow-Credentials', 'true');
      // 携带 Cookie 时不能设 *，必须指定具体源
    }
    if (exposedHeaders.length) {
      res.setHeader('Access-Control-Expose-Headers', exposedHeaders.join(', '));
    }
    res.setHeader('Access-Control-Max-Age', String(maxAge));

    // 预检请求直接返回
    if (req.method === 'OPTIONS') {
      return res.sendStatus(204);
    }
    next();
  };
}

// 使用
app.use(cors({
  origin: ['https://www.example.com', 'https://admin.example.com'],
  credentials: true,
}));

示例三：JSONP 实现

JavaScript/**
 * JSONP：利用 script 标签不受同源策略限制的特点
 * 仅支持 GET 请求，存在安全风险（XSS），不推荐新项目使用
 */
function jsonp(url, params = {}, callbackName = `jsonp_${Date.now()}`) {
  return new Promise((resolve, reject) => {
    // 将回调函数挂载到 window
    window[callbackName] = (data) => {
      resolve(data);
      cleanup();
    };

    // 拼接 URL
    const query = new URLSearchParams({
      ...params,
      callback: callbackName,
    }).toString();
    const script = document.createElement('script');
    script.src = `${url}?${query}`;
    script.onerror = () => {
      reject(new Error('JSONP request failed'));
      cleanup();
    };

    document.head.appendChild(script);

    function cleanup() {
      delete window[callbackName];
      script.remove();
    }
  });
}

// 使用
const data = await jsonp('https://api.example.com/users', { page: 1 });
// 服务端返回：jsonp_1234567890({"name": "Alice"})

示例四：postMessage 跨窗口通信

JavaScript// ====== 父页面（A 源）======
const iframe = document.getElementById('child-frame');

// 向子页面发送消息
iframe.contentWindow.postMessage(
  { type: 'INIT', data: { theme: 'dark' } },
  'https://child.example.com' // 指定目标源（安全！）
);

// 接收子页面消息
window.addEventListener('message', (event) => {
  // ✅ 始终验证 origin
  if (event.origin !== 'https://child.example.com') return;
  
  console.log('收到子页面消息:', event.data);
});

// ====== 子页面（B 源）======
// 接收父页面消息
window.addEventListener('message', (event) => {
  if (event.origin !== 'https://parent.example.com') return;
  
  if (event.data.type === 'INIT') {
    // 处理消息
    applyTheme(event.data.data.theme);
    // 回复父页面
    event.source.postMessage(
      { type: 'READY' },
      event.origin
    );
  }
});

4. 常见问题与坑点

为什么 CORS 携带 Cookie 时 Allow-Origin 不能设 *？ +

浏览器安全规范要求：当 credentials: include 时，Access-Control-Allow-Origin 必须指定具体的源，不能用通配符 *。同时 Access-Control-Allow-Credentials 必须为 true。这是为了防止任意源携带用户的 Cookie 访问资源。

预检请求（OPTIONS）失败怎么办？ +

常见原因：① 服务器未处理 OPTIONS 请求（返回 405 或 404）；② 响应头缺少 Access-Control-Allow-Headers/Methods；③ 服务器认证拦截了 OPTIONS 请求。解决方案：OPTIONS 请求直接返回 204，不经过认证中间件。

SameSite Cookie 对跨域的影响？ +

SameSite=Lax（Chrome 默认）：跨站导航（如 <a>）携带 Cookie，但跨站 Ajax/fetch 不携带。SameSite=None：跨站请求携带 Cookie，但必须配合 Secure。SameSite=Strict：仅同站请求携带。前后端分离部署在不同域时，Cookie 需设 SameSite=None; Secure。

🚫 JSONP 存在安全风险

JSONP 本质是注入 script 标签执行回调，存在 XSS 风险。恶意网站可以调用你的 JSONP 接口获取数据。新项目务必使用 CORS，JSONP 仅作为老浏览器兼容方案。

⚠ postMessage 必须验证 origin

window.addEventListener('message', handler) 会接收所有源的消息。不验证 origin 可能被恶意页面利用，造成安全漏洞。始终在 message 事件处理中检查 event.origin。

1什么是同源策略？为什么需要它？
同源策略限制不同源之间的 DOM 访问、数据读取和 Cookie/Storage 访问。需要它的原因：防止恶意网站读取用户在其他网站的数据（如银行余额）、防止 CSRF 攻击、防止点击劫持。没有 SOP，任何网站都能用 JS 读取其他网站的数据。
2CORS 的预检请求是什么？为什么需要？
预检请求是浏览器在发送"非简单请求"前自动发出的 OPTIONS 请求，询问服务器是否允许跨域。需要的原因：某些请求（如 PUT/DELETE、自定义头）可能对服务器数据产生副作用，浏览器先确认服务器是否允许，避免直接发送造成不可逆影响。
3前端跨域有哪些方案？各有什么优缺点？
CORS（标准方案，需后端配合）；代理（开发环境常用，部署时需代理服务）；JSONP（仅 GET，有安全风险）；postMessage（iframe 间通信）；WebSocket（不受 SOP 限制）；Nginx 反向代理（生产环境常用）。推荐组合：开发用代理，生产用 CORS + Nginx。
