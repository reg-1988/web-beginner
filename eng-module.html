模块化规范

从全局变量到 IIFE，从 CommonJS 到 ES Modules，模块化是前端工程化的起点——理解模块化的演进，才能理解现代前端工具链的设计。

1. 核心概念与定义

模块化是将复杂程序拆分为独立、可复用的模块的编程范式。每个模块拥有独立的作用域，对外暴露接口，对内隐藏实现细节。

模块化解决的核心问题：命名冲突（全局变量污染）、依赖管理（脚本加载顺序）、代码复用（跨项目共享）、可维护性（关注点分离）。

前端模块化经历了：全局函数 → 命名空间 → IIFE → CommonJS/AMD → UMD → ES Modules 的演进。目前 ESM 是官方标准，CommonJS 在 Node.js 中仍广泛使用。

2. 关键特性与工作原理

2.2 CommonJS 核心特性

JavaScript// 导出
module.exports = { add, subtract };
// 或
exports.add = function(a, b) { return a + b; };
// ⚠ 不能直接给 exports 赋值：exports = { add } 会断开引用

// 导入
const math = require('./math');
const { add } = require('./math'); // 解构导入

// 特性：
// 1. require() 是同步的，首次加载时执行模块，之后返回缓存
// 2. module.exports 输出的是值的拷贝
// 3. 运行时加载，无法静态分析
// 4. 循环依赖时返回已执行部分的快照

2.3 ES Modules 核心特性

JavaScript// 命名导出
export const PI = 3.14;
export function add(a, b) { return a + b; }

// 默认导出
export default class Calculator { /* ... */ }

// 导入
import Calculator, { PI, add } from './math.js';
import * as math from './math.js';
import('./math.js'); // 动态导入（返回 Promise）

// 特性：
// 1. import 是编译时静态分析，可在打包时 tree-shaking
// 2. 导出的是值的引用（绑定），源模块修改会同步反映
// 3. import 提升（类似 const 声明提升）
// 4. 顶层 this 为 undefined，不是全局对象

3. 代码示例与最佳实践

示例一：ESM 模块组织

JavaScript// ====== math.js —— 工具模块 ======
// 命名导出（推荐，便于 tree-shaking）
export function add(a, b) { return a + b; }
export function subtract(a, b) { return a - b; }
export const PI = 3.14159;

// 不推荐默认导出 + 命名导出混用
// 建议一个模块要么全部命名导出，要么仅一个默认导出

// ====== calculator.js ======
import { add, subtract } from './math.js';

export default class Calculator {
  constructor() { this.result = 0; }
  plus(n) { this.result = add(this.result, n); return this; }
  minus(n) { this.result = subtract(this.result, n); return this; }
  value() { return this.result; }
}

// ====== index.js —— 入口 ======
export { add, subtract, PI } from './math.js'; // 重新导出
export { default as Calculator } from './calculator.js';

示例二：动态导入实现按需加载

JavaScript// 路由级按需加载

  { path: '/', component: () => import('./pages/Home.vue') },

// 条件加载

  if (mode === 'advanced') {

// 交互触发加载（点击时才加载模块）

示例三：循环依赖的处理

JavaScript// ====== CJS 循环依赖 ======
// a.js
exports.loaded = false;
const b = require('./b');
exports.loaded = true;
console.log('a.js: b.loaded =', b.loaded); // false（b 还没执行完）

// b.js
exports.loaded = false;
const a = require('./a'); // 返回 a 当前的快照
exports.loaded = true;
console.log('b.js: a.loaded =', a.loaded); // false
// a.js 和 b.js 都执行完后：
// a.loaded = true, b.loaded = true（但快照中是 false）

// ====== ESM 循环依赖 ======
// a.mjs
export let loaded = false;
import { loaded as bLoaded } from './b.mjs';
loaded = true;
console.log('a.mjs: bLoaded =', bLoaded); // 取决于执行顺序

// 最佳实践：避免循环依赖！
// 解决方案：
// 1. 提取共享逻辑到第三个模块
// 2. 使用依赖注入
// 3. 延迟导入（函数内部 import）

示例五：NPM 包的模块化发布

JSON// package.json 双模式发布
{
  "name": "my-lib",
  "version": "1.0.0",
  // ESM 入口（打包工具优先使用，支持 tree-shaking）
  "module": "dist/my-lib.esm.js",
  // CJS 入口（Node.js 默认使用）
  "main": "dist/my-lib.cjs.js",
  // 浏览器入口（UMD，支持 CDN script 标签）
  "browser": "dist/my-lib.umd.js",
  // 明确声明类型
  "type": "module", // 所有 .js 文件视为 ESM
  "exports": {
    ".": {
      "import": "./dist/my-lib.esm.js",
      "require": "./dist/my-lib.cjs.js",
      "default": "./dist/my-lib.umd.js"
    },
    "./utils": {
      "import": "./dist/utils.esm.js",
      "require": "./dist/utils.cjs.js"
    }
  },
  // 声明副作用（帮助 tree-shaking）
  "sideEffects": false
}

4. 常见问题与坑点

require 和 import 可以混用吗？ +

不建议。在 ESM 文件中使用 require() 会报错（ESM 不支持 require）。在 CJS 文件中使用 import 语法需要设置 "type": "module" 或使用 .mjs 后缀。打包工具（Webpack/Vite）可以处理互操作，但运行时原生环境混用容易出问题。

ESM 的 "值的引用" 和 CJS 的 "值的拷贝" 具体区别？ +

CJS：require() 返回的是 module.exports 的浅拷贝。源模块修改变量后，引用方拿到的仍是旧值。ESM：import 建立的是绑定（binding），源模块修改变量后，引用方能读到最新值（但 import 的绑定是只读的）。

Tree-shaking 是怎么工作的？ +

Tree-shaking 依赖 ESM 的静态分析特性。打包工具在编译时扫描 import/export，标记哪些导出被使用，删除未使用的代码（dead code elimination）。CJS 的 require() 是运行时执行的，无法静态判断是否使用。需确保：使用 ESM 语法、package.json 设置 sideEffects、避免动态导入路径。

🚫 不要在 CJS 中给 exports 赋值

exports = { a: 1 } 会断开 exports 和 module.exports 的引用关系，导致导出失效。正确做法：module.exports = { a: 1 } 或 exports.a = 1。

⚠ ESM 文件必须带后缀

浏览器中 ESM 的 import 路径必须是完整 URL 或相对路径带 .js 后缀。Node.js 中 CJS 的 require 可以省略后缀，但 ESM 的 import 不行（除非配置了 exports 字段）。推荐始终写明后缀。

1CommonJS 和 ES Modules 有什么区别？
① CJS 运行时加载，ESM 编译时静态分析；② CJS 输出值拷贝，ESM 输出值引用；③ CJS 的 require 同步，ESM 的 import 异步；④ ESM 支持 tree-shaking，CJS 不支持；⑤ ESM 顶层 this 为 undefined，CJS 为 module.exports；⑥ ESM 支持顶层 await。
2什么是 Tree-shaking？为什么 ESM 支持而 CJS 不支持？
Tree-shaking 是删除未使用代码的优化。ESM 的 import/export 是静态声明，编译时可确定依赖关系，打包工具能安全删除未使用的导出。CJS 的 require() 是运行时执行，可能包含条件逻辑，无法静态判断哪些模块会被加载。
3如何实现模块的按需加载？
ESM 的动态 import() 返回 Promise，可实现运行时按需加载。应用场景：路由懒加载、条件加载、交互触发加载。Webpack 将 import() 自动拆分为独立 chunk，Vite 也原生支持。配合 Suspense/Loading 状态提供良好用户体验。
